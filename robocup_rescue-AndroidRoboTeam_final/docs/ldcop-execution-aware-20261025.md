## 共性问题：能确认什么、还不能确认什么

1. **改派改变了搜索/访问覆盖。** Berlin确实救到了原版消防没直接看到的平民；
   Eindhoven漏掉一个原版能救活的人；Paris/Sakae的新增和损失人员同时很多。
   不能从这些结果推出“每次升分都来自更快路径”。
2. **局部虚拟排程不等于队友执行。** Istanbul的709853563在救护第24步队列中出现，
   但消防实际第153步才开始救，原版第104步就开始。
   旧实现会为同角色其他人分配任务、为忙着执行另一目标的人安排新任务，且没有把最终保底选择完整反馈给规划器。
3. **重埋压任务需要协作，但远程无上限聚集又浪费覆盖。** Berlin的425731071双方第20步开挖，
   原版两人第49步脱困，上一轮单人第78步脱困并于79步死亡。
   Istanbul部分晚到目标又出现24～31条同一步消防救援指令；晚来一大群并不能补回之前的几十步。
4. **12个候选先截断再验可行，容易忽略近处可救对象。** 截止时间靠前但路远/时间窗已不可行的任务，
   与所有未确认执行的未来任务混在一起，会挤占候选池。

这些机制有代码与日志支持；各项对最终分差的精确贡献仍需分别消融。

## 本次具体改动：仅非 original 项目

仍使用已有L-DCOP分层插入排程、时间窗校验与普通通信，不加入新的DCOP求解器。
不按地图名开关策略，不修改场景、人数、随机种子、服务器评分或正式比赛步数。

### 1. 用真实最终意图协调，限制影子任务

- 单个Agent只调度本角色自己的队列，不再假定同角色其他空闲人已接受本地安排。
- 非本角色的工人必须有近期信息；救护预排被埋压平民还需近期真实消防目标意图。
- 已有目标的队友不能在本地模型里被重派到另一个目标。
- 本地优先/规划/保底最终确定目标后，才刷新和广播意图；不再广播随后未采用的提案。
- 保留本地立即施救/装载与原有保底选择，不把全部行为交给严格排程。

普通无线意图仍不等于可靠执行确认；掉包、行动受阻和临时休息仍可能带来偏差。
本次没有声称实现了可靠的跨进程全局一致性。

### 2. 有边界的重埋压协助和工期估算

- 只有近期救援状态、同地点、健康且未被埋的消防计入正在工作的协作人数。
- 工期用 `ceil(剩余埋压/当前可信参与人数)`，不把每个被分配过的人当作已到场。
- 对埋压≥40的实际作业目标，附近空闲消防可协助；默认最多3个已认领远程参与者、助援路程≤8步，
  且预计至少节省4步。按距离/ID挑选有限增援名额，不对所有消防广播无条件增援。
- 对轻埋压但存活窗口已经不足以单人救出的目标，按扣除估计运输时间后的救援窗口提高所需人数，
  不因埋压未达40就阻止紧急协助；此时至少应有1步预计收益。
- 多人同时认领时，远程名额按距离/ID保留，超额认领者重新选人或搜索；不允许每个人都以
  “我已认领”为由无限占位。已到现场可立即施救者仍不被无线估计强行赶走。
- 近处已经能直接施救的人不因无线人数估计而被强行赶走；这个远程上限不是对现场人数的绝对承诺。
- 已有有效任务的Agent不被随意拉去助援，正在增援的目标也不会每步被无关新任务打断。

### 3. 候选池兼顾紧急和近期可完成任务

- 先做乐观行程/服务时间可行性筛选，再应用12个候选上限。
- 约1/3名额保留截止时间紧的对象，其余按较早可完成时间补入；保留仍可行的当前执行目标。
- 不把无实际消防意图的被埋压者提前当成确定将被救出的运输任务。
- 这些仍是有限信息下的估计，不是直接最优化服务器完整非线性得分。

### 4. 保底也共享占用信息

保底选人沿用原来的优先级/距离顺序，但跳过已经有足够近期远程认领者的目标；
救护不追逐一个已有更近可信承运者的远方目标。这样未被占用的队员可以选择其他人或继续原有搜索。
本地立即装载/救援不被此远程筛选阻塞，避免错过眼前窗口。
